权限与审批机制 · 五家统一分档研究

Claude Code × Codex × CodeBuddy × TRAE × OpenClaw
权限模式统一分档

在 Claude Code / Codex / CodeBuddy 三家对比的基础上加入 TRAE 与 OpenClaw，验证一个结论：这五套彼此独立的权限机制，能否收敛到同一套档位模型，以及每家在每一档上分别对应什么配置。

数据截止 2026-09-18 证据来源 五方官方文档站一手内容 结论可信度 高

核心结论

4 档模型对五家全部成立，且 OpenClaw 官方文档印证了本报告对 Codex 的映射。

五家的全部用户可选模式都能落进同一个 4 档模型。TRAE 与 TraeWork 一样，恰好只有 3 档（手动审批 / 自动审批 / 完全访问），缺的同样是第 2 档；OpenClaw 粒度最细，是"沙箱 3 档 × 审批 5 档"的完整二维矩阵。最有意思的是，OpenClaw 的 mode="auto" 官方明确映射到 Codex 的 approvalPolicy=on-request ＋ approvalsReviewer=auto_review ＋ sandbox=workspace-write，与本报告独立推导出的 Codex 第 3 档配置完全一致。

五家的收敛度超出预期 沙箱层三家（Claude Code、CodeBuddy、TRAE）都复用 OS 原语，TRAE 甚至明确写出 macOS sandbox-exec / Linux Bubblewrap + User Namespace；审批层四家（Claude Code、CodeBuddy、TRAE、OpenClaw）都有"LLM 判定"档；"完全访问"五家全有且全部标注仅限隔离环境。真正分歧不在"有没有这些档"，而在默认值与第 3 档由什么判定。

统一分档模型

分档轴只有一条：哪些动作会被自动放行，以及放行不了时由谁裁决。四档如下，从最保守到最放开。

关键发现

发现一：默认值的差距横跨三档

这是五家最实质的分歧。同样叫"默认"，实际放行强度从第 1 档一直到第 4 档。

产品默认落档默认状态
OpenClaw第 4 档沙箱默认 off，且 gateway / node 的 exec.security 默认 full、exec.ask 默认 off。官方原文："No-approval host exec is the default for gateway and node"。
Claude Code第 3 档消费级计划默认 auto（v2.1.228+）；claude -p、Agent SDK、Bedrock 等场景默认第 1 档。
TRAE第 3 档旧体系「沙箱运行（支持白名单）」默认启用，命令在沙箱内自动运行。
Codex第 2～3 档之间默认 workspace-write ＋ on-request：沙箱内自动，越界由人审批。
CodeBuddy第 1 档默认 default，官方表述为"默认使用严格的只读权限"。

五家里只有 CodeBuddy 把默认值放在最保守档，OpenClaw 反而默认就在最放开档。若把"默认档位"当作产品安全姿态的代理指标，这五家的排序与它们各自的安全宣传口径并不一致。

发现二：第 3 档内部有两类判定器

第 3 档的共性只是"越界不由人裁决"，但"由什么裁决"分成两支，能力与可预期性差异明显。

确定性规则 / 白名单可预期，但覆盖窄

  • TRAE「沙箱运行（支持白名单）」：白名单命令直接放行，其余在沙箱内自动运行并做风险判定，内置 commandAstDangerChecker 语法分析检测 rm -rf /、chmod 777 等
  • OpenClaw 的 allowlist 语义：白名单直接跑，未命中静默拒绝
  • Codex 的 untrusted：只自动放行"已知安全"的只读操作
  • 优点：行为完全可预期、可审计、无模型不确定性；缺点：覆盖窄，长尾命令仍会弹窗

LLM 判定覆盖广，但非确定性保证

  • Claude Code 的 classifier、CodeBuddy 的分类器：读自然语言可信边界，fail-closed
  • Codex 的 auto_review：独立 reviewer agent，含拒绝熔断
  • TRAE「自动审批」：内置 LLM Guardian（用自定义模型时由该模型审批）
  • OpenClaw 的 exec.mode="auto"：交原生自动审查器
  • 三家都明确自陈局限：Codex 称"不是确定性的安全保证"，OpenClaw 称"这不是一个完美的安全边界"

发现三：OpenClaw 官方印证了 Codex 的映射

本报告对 Codex 第 3 档的映射是 workspace-write ＋ on-request ＋ auto_review。OpenClaw 官方文档在"Codex Guardian mapping"一节中，把它自己的 exec.mode="auto" 明确定义为映射到 Codex 的 approvalPolicy=on-request、approvalsReviewer=auto_review、sandbox=workspace-write。两个独立来源得出同一组合，这既验证了本报告的映射，也说明"沙箱内自动 ＋ 越界 LLM 复审"已经成为跨产品的标准第 3 档形态。

发现四：OpenClaw 有独一份的"双层取严"机制

OpenClaw 的有效策略由配置层（tools.exec.*）与主机本地审批状态两处派生，取更严格的一方；且审批只能收紧、不能放松配置派生的安全策略。命令获批后会绑定规范执行上下文（cwd、精确 argv、env、可执行文件路径与内容哈希），若审批到执行之间解析发生变化则拒绝运行。这套"配置与本地审批互相制约"的设计，在其余四家的单层配置模型中都没有对应物。

TRAE 专章

它有两套并存的权限体系

这是评估 TRAE 时最容易混淆的一点：新旧两套体系同时存在，且都对外可见。

新体系 · Beta权限审批

  • 入口：设置 > Beta > 启用权限系统；启用后出现在设置 > 权限审批
  • 三档：手动审批 / 自动审批 / 完全访问，另支持自定义权限模式
  • 与 TraeWork 的档位命名完全一致，自动审批同样由内置 LLM Guardian 判定
  • 状态：Beta，默认关闭；官方原文"关闭后将使用旧版自动运行设置"
  • 企业版不可用：功能清单中「权限审批」为个人版可用、企业版不可用

旧体系 · 默认生效自动运行

  • 入口：设置 > 对话流 > 自动运行
  • 三档：沙箱运行（支持白名单）/ 手动运行 / 自动运行
  • 「沙箱运行」默认启用：命令在沙箱中自动运行并判定风险，白名单命令无需经过沙箱直接运行
  • 「自动运行」官方风险原文："建议非必要不启用 '自动运行' 模式。该模式会跳过所有安全检查，可能导致高风险操作在无提示的情况下被执行。"
  • 可按 IDE 模式 / SOLO 模式分别设置；「自动运行 MCP」为独立开关
一个值得注意的落差 TRAE 的新三档与 TraeWork 完全同名同义，但它只对个人版开放。企业版没有这套 UI，只能靠管理员侧的企业命令黑名单 ＋ 企业沙箱 ＋ 客户端旧「自动运行」设置来做管控。也就是说，企业客户目前拿不到"手动审批 / 自动审批"这种档位化的体验，而个人版用户可以。这是本次五家对比中唯一出现的"分档能力与版本/套餐绑定"的情况。

沙箱实现是五家里最"本土化"的

TRAE 没有像其他几家那样统一走 Seatbelt ＋ bubblewrap，而是按平台分别实现：macOS 用系统 sandbox-exec，Windows 用自研沙箱 SDK，WSL2/Linux 用 Bubblewrap + User Namespace（Debian 10+ / Ubuntu 20.04+，通过 Remote SSH），远程 Linux 还会自动写入 /etc/sysctl.d/trae-sandbox.conf。它是五家里唯一在原生 Windows 上提供沙箱的（Claude Code 完全不支持原生 Windows 沙箱，CodeBuddy 计划中，OpenClaw 依赖 Docker）。

文件系统边界也最"白名单化"：项目目录内 .trae、.vscode、.git 被排除在读写之外；根目录 / 默认只读，所有未显式声明为可写的目录均为只读；读写权限继承当前用户权限，读写与只读冲突时以只读为准。需要注意官方明确"当前系统内置安全策略不涉及网络访问"，网络控制在 sandbox.json 中仅 Windows 生效。

企业管控是五家里最完整的

  • 企业命令黑名单：文本匹配，"只要命令的任何部分（前缀、中间、结尾）匹配到黑名单文本，该命令就会被拦截"；一次工具调用中任一条命中则整批禁止。优先级为企业黑名单 > 个人白名单 > TRAE 内置默认规则。生效延迟约 10 分钟，需旗舰版。
  • 企业沙箱：按 Windows / macOS / Linux 分别下发策略（JSON，含 filesystem、network），官方明确"企业沙箱配置的优先级高于成员的个人沙箱配置"；同一操作系统只能启用一个策略；网络访问控制目前仅支持 Windows。
  • 覆盖范围为五家最广：TraeCode / TraeWork 桌面＋网页 / TRAE 移动端 / Plugin / CLI。

OpenClaw 专章

它是唯一把"三层"讲清楚的产品

OpenClaw 官方把权限拆成三个互相独立的问题，这是五家里表述最清晰的一套：

  • Sandbox（在哪跑）：agents.defaults.sandbox.mode = off（默认）/ non-main / all；后端默认 Docker，另有 Podman / SSH / OpenShell / Crabbox；作用域 session / agent（默认）/ shared；工作区访问 workspaceAccess = none（默认）/ ro / rw。Gateway 进程始终留在宿主机，只有工具执行被移入沙箱。
  • Tool policy（哪些工具存在）：五层过滤，逐层只能收紧，deny 永远优先；若 allow 非空则其余一律视为被阻止。tool policy 是硬停止，/exec 无法覆盖被 deny 的 exec 工具。
  • Elevated（exec 专用逃逸口）：默认跑在 gateway，需 tools.elevated.enabled ＋ tools.elevated.allowFrom.<provider> 双重门控。

审批层则是 5 档的 tools.exec.mode：deny / allowlist / ask / auto / full。这套设计的好处是"能做什么"与"问不问人"彻底解耦，坏处是概念数量最多、上手成本最高。

它的默认值是五家里最放开的

官方明确：沙箱默认 off；gateway / node 主机的 exec.security 默认 full、exec.ask 默认 off，即默认无审批、无沙箱。官方原文："No-approval host exec is the default for gateway and node"。同时官方也在文档中做了大量自我限定：

官方自陈的三条边界 "这不是一个完美的安全边界"（This is not a perfect security boundary, but it materially limits filesystem and process access when the model does something dumb.）
"每个 gateway 只有一个信任边界"：OpenClaw is not a hostile multi-tenant security boundary for mutually adversarial users sharing one agent or gateway.
"审批不是认证边界"：Approvals reduce accidental execution risk, but are not a per-user auth boundary or filesystem read-only policy.
官方还特别说明：运行 security="full" 且 ask="off" 的 node "遵循默认的可信操作员模型，是预期行为而非缺陷"。

三个别家没有的机制

  • 双层取严：有效策略由配置层 tools.exec.* 与主机本地审批状态两处派生，取更严格的一方；审批只能收紧、不能放松配置派生的安全策略。审批状态从早期 exec-approvals.json 迁移到了共享 SQLite 的 exec_approvals_config 行。
  • 审批绑定执行上下文：命令获批后绑定规范执行上下文（cwd、精确 argv、env、固定可执行文件路径与内容哈希），若审批到执行之间解析发生变化则拒绝运行。这防的是"批的时候是 A，跑的时候变成 B"的经典 TOCTOU 问题，五家里只有 OpenClaw 显式做了这件事。
  • 把 Codex / Claude Code 当后端并接管其权限：mode="auto" 会驱动 Codex app-server 走 Guardian 审查，并强制覆盖 Codex 原有的 sandbox / approval 配置，避免残留 approvalPolicy:"never" ＋ sandbox:"danger-full-access" 这类不安全组合；deny / allowlist 会完全阻断 Codex 的本地执行。接 Claude Code 时则只用其 exec allowlist 校验命令参数，不接管沙箱。

额外拦截项

strictInlineEval（默认 false）开启后，内联代码求值形式（python -c、node -e、ruby -e、perl -e、php -r、lua -e、osascript -e，以及 awk/sed/make/find -exec/xargs 的内联形式）必须经审查器或显式人工审批。host 执行还会拒绝 env.PATH 与 LD_*/DYLD_* 覆盖，防二进制劫持。bind mount 默认阻断 /etc、/proc、/sys、/dev、/root、/boot、Docker socket 目录以及 HOME 下的凭据子路径（.aws、.docker、.ssh、.gnupg、.npm 等）。

对 TraeWork 的建议

加入 TRAE 与 OpenClaw 之后，此前的建议需要做两处修正。

  • 补第 2 档仍然成立，且更有必要。五家里只有三家（Claude Code、CodeBuddy、Codex）能原生表达"编辑自动、命令问人"。TRAE 与 OpenClaw 都需要额外配置。这说明第 2 档是行业普遍缺口而非个别产品缺失，谁能先做成一等公民，谁就多一个明确的差异化点。
  • 优先解决 TRAE 自身的"新旧双轨"问题。TRAE 目前新旧两套权限体系并存，新三档还是 Beta 且企业版不可用。对 TraeWork 而言，真正的对手不是 Claude Code，而是同门的旧「自动运行」三档：两套档位命名相似、语义重叠、默认值不同，用户与企业管理员极易混淆。建议明确收敛时间表与迁移路径。
  • 第 3 档的判定器需要显式定义并对外说明。五家分成"确定性规则"与"LLM 判定"两支，而 TRAE 是唯一两支并存的（旧体系规则判定为默认，新体系 LLM Guardian）。若 TraeWork 走 LLM Guardian 路线，应像 Codex 一样公开熔断阈值与策略边界，像 Claude Code 一样明确"判定层不读项目内配置"，并像 OpenClaw 一样说明"审批不是认证边界"。
  • 把"第 4 档是否保留硬红线"写成明确的产品承诺。五家中三家（Claude Code、CodeBuddy，以及分两层的 TRAE 旧体系）在第 4 档保留了一定拦截，两家（Codex、OpenClaw）彻底放开。这是一个必须显式表态的取舍，不能留白。
  • 企业版分档能力值得补齐。TRAE 的企业命令黑名单与企业沙箱（按 OS 下发、优先级高于个人配置）在五家里最完整，值得借鉴；但其新「权限审批」UI 企业版不可用，是明显短板。建议 TraeWork 在企业版同时提供"档位选择 ＋ 管理员强制下限"两层能力。
  • 可借鉴 OpenClaw 的"审批绑定执行上下文"。命令获批后绑定 cwd、精确 argv、env 与可执行文件哈希，解析变化即拒绝运行。这是防止审批被绕过的高性价比加固，且不增加用户侧的操作负担。
