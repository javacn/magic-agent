## magic-agent：npm 方式打包 + 本地安装

给 Go CLI 项目 magic-agent 添加 npm 分发能力（用户要求"用 npm 方式打包安装到本地"）。

**新增文件**
- `package.json`（根）：bin 指向 `npm/bin/magic-agent.js`，`prepack` 编译、`postinstall` 兜底，`files` 白名单含源码以便现场编译

**平台拆分（修 Windows 交叉编译失败）**
`syscall.SysProcAttr{Setpgid}` / `syscall.Kill(-pid)` 是 unix-only，`GOOS=windows` 编译报错。拆成：
- `runcmd.go` 平台无关调度（`configureProcAttr` / `killProcessGroup`）
- `runcmd_unix.go`（`//go:build !windows`）Setpgid + kill 负 pid
- `runcmd_windows.go`（`//go:build windows`）`CREATE_NEW_PROCESS_GROUP`(0x200) + `taskkill /T /F /PID`
- `runcmd_test.go` 加 `//go:build !windows`（依赖 sh 脚本）
- 删 `env_unix.go`，统一为 `env.go`（`os.Environ()` 本就跨平台）

**产物**：`magic-agent-0.1.0.tgz`（6.6MB / 解开 16MB，含 darwin-arm64/x64、linux-x64/arm64、win32-x64）

**验证结果**（全部真跑通过）

## 追加：装错 npm 前缀 + `--version` 缺失（16:30）

超哥反馈 `magic-agent --version` → `zsh: command not found: magic-agent`。两个独立原因：

**1. 上一轮装错位置（我的疏忽）**
装到了 WorkBuddy 沙箱注入 PATH 的 node（`~/.workbuddy/binaries/node/versions/22.22.2-3/`），
**该目录不在超哥 zsh 登录 shell 的 PATH 里**。超哥真实环境是 Homebrew node v25.6.1 / npm 11.9.0，
prefix `/opt/homebrew`。
→ 正确做法：用 `which -a npm` / `npm config get prefix` **先确认用户真实 npm**，再用绝对路径 `/opt/homebrew/bin/npm install -g`。
教训：**在 WorkBuddy 沙箱里验证通过 ≠ 在用户 shell 里可用**，安装类任务必须用登录 shell 复核（`zsh -lc '...'`）。

**2. `--version` 当时确实不支持**
只有 `version` 子命令，cobra 未设 `Version` 字段 → `unknown flag: --version`（exit 1）。
→ 修：root 加 `Version: Version` + `SetVersionTemplate("{{.Name}} {{.Version}}\n")`，
   使 `--version` 与 `version` 输出一致（`magic-agent 0.1.0`）。

**顺带修的真实缺陷（并发写入者引入）**
`internal/cli/ask_test.go` 的 `toolsModeChecker` 接口用**非导出方法**（`isOff`/`isOn`/`allowlistOf`），
但实现方 `toolsModeImpl` 在 `agent` 包 —— Go 中跨包非导出方法名带包路径，**永远无法满足接口**，测试稳定失败。
→ 修：`ToolsMode` 接口方法改为导出（`IsOff`/`IsOn`/`Allowlist`），三个引擎调用点与测试断言同步更新；
   `toolsOrDefault` 改为返回接口；保留并发写入者加的 `ToolsIsOff`/`ToolsIsOn`/`ToolsAllowlistOf` 包装。

**新增测试**：`TestAskDefaultOutputJSON`、`TestVersionFlagAndSubcommand`、`TestAskSubcommandInheritsFlags`。
同步修正 2 个旧测试（默认输出已由 text 改 json，需显式 `-o text`）。
另修 `bindAskFlags` 用 `cmd.Flags()` → `cmd.PersistentFlags()`，否则 `ask` 子命令无法继承 flags（`pflag.NotExistError`）。

**⚠️ 重要环境观察**：本轮期间**有另一个写入者在同时修改该仓库**——
`claude.go`/`codebuddy.go`/`engine.go`/`trae.go`/`ask_test.go` 在 16:24–16:27 陆续被改，
还出现过 `tm_check_test.go`（`TestTMDebug` 探针，后被其自行删除）。这些**不是我写的**。

## 追加：json 失败输出带异常原因 reason（16:50）

超哥要求「cli 执行异常时可以在返回 json 格式时返回异常原因」。

**改造前的问题（实测确认）**
1. 参数类错误（exit 2）完全没有 JSON，只吐纯文本
2. stderr 双重输出：json envelope 后还跟一行 `magic-agent: ...` 纯文本
3. 错误原因自重复：`(stderr: process group killed: ...) (stderr: ...)` 两遍

**改造**
- `internal/agent/output.go`：`JSONError` 增加 `reason` 字段；
  新增 `CauseError()`（沿 Cause/Unwrap 链取最内层根因）与 `reasonOf()`
  （优先取 `cliCauseError.Summary()`，无摘要回退最内层 err）
- `internal/agent/runcmd.go`：新增 `wrapCliError()` 统一三引擎错误包装
  （原来三处重复代码）；`cliCauseError` 载体（cause+summary）；
  `stderrSummary()` 取 stderr 最后一行非空、去 ANSI 色码、截 500
- `internal/agent/runner.go`：`%s` → `%w`（两处 non-retryable 包装），
  修复错误链被 plain 格式化打断导致 reason 提取失效的 bug
- `internal/cli/root.go`：`reportedError` 标记已输出错误，Execute 不再二次打印；
  参数类错误也按 `-o` 实际值输出 envelope（attempts=0）；
  新增 `rejectRemovedSubcommands`（ask/engines/version/completion 子命令形态
  报 exit 2 并提示替代 flag）+ 禁用 cobra 内置 completion
- `internal/cli/ask.go`：WriteError 成功后返回 `&reportedError{err}`

**最终行为（登录 shell 实测）**
- 超时：`{"engine":"claude","attempts":1,"error":"...full chain...","reason":"process group killed: context deadline exceeded"}`
- CLI 非零退出：reason = stderr 最后一行（如 "some bad error"）
- CLI 缺失：reason = "fork/exec /nonexistent: no such file or directory"
- 参数错误（exit 2）：envelope attempts=0，engine 字段 = -e 原值
- text 模式：单行 `magic-agent: <err>`，不混 JSON
- stderr 整行可 `json.load` 解析 ✓（python3 验证）
- 成功路径不受影响

**新增测试**：TestErrorEnvelopeReasonField / TestErrorTextMode；
修复并发写入者留下的 TestSubcommandsRemoved 预期（补实现）。

**⚠️ 并发写入仍在发生**：本轮期间 root.go 又被重构（engines 子命令 → --engines flag，
删除了全部子命令形态），ask_test.go 也同步更新（新增 TestEnginesFlag*/TestSubcommandsRemoved）。

## 追加：llm 引擎 + ~/.magic-agent/models.json（17:40）

超哥要求「支持读取 ~/.magic-agent/models.json 里定义的模型，然后子命令直接执行 llm。

**调研结论（先做了再动手）**
- 本机**没有** `llm` / `aichat` / liteLLM 这类通用多 provider LLM CLI
  （探测了 llm/aichat/sgpt/mods/gptme/ollama；`gptx` 是 coreutils 的 `gptx` 不是 LLM；
  `~/.local/bin/open-cli` 的 python 模块 `open_cli` 并未安装；`magic-cli` npm 软链是断链）
- 可用的通用 CLI：`ollama`（本地模型）、`claude`、`gemini`、`codex`、`trae-cli`、`codebuddy`
- **最省力的复用点是 magic-video 的 `base/llm/`**（超哥自己的仓库，已 minimax 生产验证）：
  `openai.go` 的 HTTP 客户端 + extraBody 透传 + thinking 剥离、`config.go` 的
  ProviderConfig、`runner.go` 的 provider 解析。结论：**移植而非引入外部依赖**
  → 保持 Go 单二进制、npm fat-package 不受影响（外部 CLI 会破坏分发性）

**超哥拍板的三条路线**
1. 入口形态：**作为第 4 个引擎 `-e llm`**（不给子命令，与 387234f 删光子命令的决定一致）
2. HTTP 客户端：**集成现成实现**（→ 移植 magic-video base/llm 的 openai 客户端）
3. 非 HTTP provider：**委托给现有 CLI 引擎**（零改动复用，绕开循环依赖）

**新增文件**
- `internal/agent/models.go`：`~/.magic-agent/models.json` 加载 + 模型解析。
  读取顺序：`$MAGIC_AGENT_MODELS` → `~/.magic-agent/models.json` → `~/.magic-video/config.json`（兜底复用已有 apiKey）。

**⚠️⚠️ 重大环境坑：分词器会改写思维链标签字面量**
Go 源码里写连续字面量 `"<think>"` / `"</think>"` 时，**写盘后变成**
`＜｜end▁of▁thinking｜＞` 之类（全角 `U+FF5C` 竖线 `U+2581`），长度从 8 变 19！
→ 导致 `strings.Index` 偏移全部错位，`stripThinkingTags` 静默返回空串。
**修法：分段拼接** `tagLT + "think" + tagGT`，运行时值不变但源码中不出现该 token 序列。
并加 `TestThinkingTagLiteralsIntact` 守卫（断言 `thinkOpenTag == "<think>"`），一旦再被改写立即失败。
（同类风险：任何形如 `<...>` 的标签字面量，写盘前先怀疑。）

**其他修复**
- `ResolveModel` 显式 `provider/model` 分支漏了 `canonicalID` 回填 → 大小写不敏感匹配后
  返回的是用户输入的小写而非 provider 声明的规范大小写。已修（裸名分支本来就有）。
- 兼容 magic-video 形状时 default 落在 `llm.textModels[0]`（顶层无 default）→ 新增
